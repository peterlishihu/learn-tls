## 0. 先回答一个根本问题：为什么应用可以像 TCP 一样随意读写？

TLS 记录确实有长度、线上确实是「一帧一帧」的。但**应用感知不到这一点**，因为 TLS 库在两个方向各做了一次转换：

```
应用 write(100 KB，任意长度)          应用 read(&mut buf[n])   ← 任意 n，允许短读
        │                                       ▲
        ▼                                       │ 从明文缓冲区拷贝，
┌──── TLS 发送端 ────┐                  ┌──── TLS 接收端 ────┐  可跨记录边界
│ ① 自动分片：        │                  │ ③ 逐条解密记录      │
│   100 KB → 7 条记录 │   TCP 字节流     │ ④ 去掉记录头，明文  │
│ ② 每片独立加头+加密 │ ───────────────▶ │   追加进内部缓冲    │
└────────────────────┘                  └────────────────────┘
```

- **发送**：`write()` 的 buffer 被按 16 KiB 切块，每块独立加记录头、独立加密。应用从不接触「记录」概念。
- **接收**：解密后的明文被**拼接**进一个缓冲区，`read(buf)` 一直拷贝到「buf 满」或「明文耗尽」为止——自然跨越记录边界，语义与 TCP `read` 完全一致（含短读）。
- 甚至**握手还没完成时的 write 也会被接受**：先缓存在 TLS 库内部，握手一完成立即发出（rustls 中是 `sendable_plaintext` 缓冲，见核对表）。

**关键推论（重要，常被误解）**：

> 记录边界 ≠ 消息边界。发送端 `write()` 的边界**不保证**对应接收端 `read()` 的边界
> （分片点、中间的握手记录插入都可能改变它）。所以上层协议仍然需要自己的边界协议
> ——HTTP 用 `Content-Length`/chunked、Redis 按行、自定义协议用长度前缀——**和在裸
> TCP 上完全一样**。TLS 只提供加密 + 完整性，不提供消息框架。

类比：TCP 本身也是把你的流切成 MSS 大小的段塞进 IP 包，你却把 TCP 当流用。**record 就是 TLS 层的 "MSS"**。

## 1. 记录的线上格式（逐字节）

### 1.1 头部固定 5 字节

```
 0                    1                    2                    3
┌────────────────────┬────────────────────┬────────────────────┬───┐
│ 内容类型 (1 byte)  │ 版本 (2 bytes)     │ 长度 (2 bytes)     │载荷│
└────────────────────┴────────────────────┴────────────────────┴───┘
   例: 0x17 (AppData)   0x03 0x03           0x00 0x75 (117)
```

| 字段 | 大小 | 含义 |
|------|------|------|
| content_type | 1 B | 这条记录装的是什么（见 1.2） |
| legacy_version | 2 B | **兼容性摆设**，见 1.3 |
| length | 2 B | 载荷字节数（密文场景=密文长度，含认证标签） |

### 1.2 内容类型（IANA 注册值）

| 值 | 名称 | 用途 |
|----|------|------|
| 20 (0x14) | ChangeCipherSpec | TLS ≤1.2 的换钥信号；1.3 仅作中间盒伪装 |
| 21 (0x15) | Alert | 告警/关连接（有密钥后也加密传输） |
| 22 (0x16) | Handshake | 握手消息（有密钥后加密传输） |
| 23 (0x17) | ApplicationData | 应用数据；**TLS 1.3 中一切加密记录在线上都伪装成 23** |
| 24 (0x18) | Heartbeat | TLS 1.2 心跳扩展（rustls 不支持） |

**TLS 1.3 的「类型伪装」**：握手一旦有了密钥，后续的握手消息、alert、Key Update 全部装在 content_type=23 的记录里，**真实类型作为 1 字节附在明文末尾一起加密**（见 §4.2）。线上观察者只知道「这是一条加密记录」，连它是握手还是应用数据都不知道。

**一条记录 ≠ 一条消息**：握手消息可以跨记录拆分，也可以多条合并在一条记录里发（RFC 8446 §5.1）。这再次印证 §0 的推论——记录只是运输容器。

### 1.3 版本字段：为什么 TLS 1.3 的记录写 0x0303？

RFC 8446 把这个字段改名为 `legacy_record_version` 并规定：**除了最初的 ClientHello 可以写 0x0301 外，所有记录一律填 0x0303（TLS 1.2）**。原因：大量中间盒（旧防火墙/NAT）按记录版本字段做过滤，写 0x0304 会被掐断。真正的版本协商发生在 ClientHello 的 `supported_versions` 扩展里（课时1）。

接收方也不该信这个字段：rustls 入站只要求高字节是 0x03 就接受，版本以握手协商结果为准。

### 1.4 长度字段的边界（三个数字，别混）

| 场景 | 上限 | 出处 |
|------|------|------|
| 明文片段（加密前） | 2¹⁴ = 16384 B | RFC 8446 §5.1 / RFC 5246 §6.2.1 |
| TLS 1.3 密文记录（线上 length 字段） | 2¹⁴ + 256 | RFC 8446 §5.2（明文+类型+填充+16B 标签） |
| TLS 1.2 密文记录 | 2¹⁴ + 2048 | RFC 5246 §6.2.3（容纳 CBC 填充/IV 或 GCM 显式 nonce+标签） |

超限 → 接收方必须回 `record_overflow` alert 断开。rustls 入站按最宽的 16384+2048 校验（见核对表）。

**空记录规则**：非 ApplicationData 的零长度记录直接拒绝；TLS 1.3 中解密后至少有 1 字节（真实类型字节），rustls 也从不主动发空记录。

### 1.5 完整示例：100 字节 HTTP 请求的一条 TLS 1.3 记录

```
明文（应用交给 TLS）:  "GET /index.html HTTP/1.1\r\n..."  共 100 字节

① 构造内部明文:      100 字节内容 + 1 字节真实类型 0x17 + 0 字节填充 = 101 字节
② AEAD 加密:          密文 101 字节 + 16 字节认证标签 = 117 字节
③ 加记录头:           17 03 03 00 75
                        │  │  │  └── 117 (0x0075)
                        │  │  └───── 0x0303 (伪装成 1.2)
                        │  └──────── 0x03
                        └─────────── 0x17 (AppData)
线上总计:             5 + 117 = 122 字节
```

## 2. 分片与重组

### 2.1 为什么要有最大长度限制？

1. **内存 DoS 防御**：接收方必须在验证认证标签**之前**按 length 字段缓冲整条记录。没有上限，一个恶意 length 就能让接收方疯狂分配内存。
2. **密码学需要**：MAC/AEAD 作用于有界数据，每条记录要独立算标签、独立取 nonce，无法对无限流做认证。
3. **延迟与缓冲预算**：限制单条记录大小 → 限制单次加解密的延迟抖动 → 实现可以预分配固定大小缓冲。

### 2.2 分片的算术

`write(100_000)`（约 97.7 KiB）→ ⌈100000/16384⌉ = **7 条记录**：前 6 条各装满 16384 B 明文，第 7 条装 1696 B。每条独立加头、独立加密。接收端解密后把 7 段明文拼回一个连续缓冲区——边界就此抹掉。

### 2.3 记录大小可以协商（两个机制）

| 机制 | 版本 | 取值 | 说明 |
|------|------|------|------|
| `max_fragment_length` 扩展（RFC 6066） | 1.2/1.3 | 512/1024/2048/4096 四档 | 为内存受限设备设计 |
| `record_size_limit` 扩展（RFC 8449） | 1.3 | 64..16384 任意 | 更细粒度，常用于对齐路径 MTU |

rustls 支持 `set_max_fragment_size()`（32..=16389，**含 5 B 记录头、不含加密开销**），对应前者；暂不支持 RFC 8449。

**流量分析视角**：长度字段不加密，记录长度本身泄露信息（页面大小、按键时序…）。TLS 1.3 内部明文支持填充（§4.2），就是为了把长度「抹平」一点；缩小 max_fragment_size 也有类似效果。

### 2.4 记录大小与底层传输的关系（MSS / MTU / QUIC / DTLS）

| | TCP MSS | TLS 记录上限 |
|---|---|---|
| 取值来源 | 路径 MTU 推导（MTU−40），每连接可不同 | 协议常量 2¹⁴，RFC 硬性规定 |
| 可协商性 | 内核按路径调整 | 只能调小不能调大（§2.3） |
| 存在目的 | 避免 IP 分片 | 接收方内存防 DoS + 密码学有界单元 |
| 超限后果 | 内核自动分段，无错误 | `record_overflow` alert 断连 |

**记录超 MSS 无害**：16 KB 记录被 TCP 切成约 12 个段，不会引起 IP 分片（对 TCP 而言记录只是流里的字节）。但两者在**丢包**上耦合：AEAD 标签在记录末尾，整条记录的所有段到齐才能解密——丢 1 个 MSS 段，16 KB 记录整体卡住（记录层队头阻塞 / 丢包放大）。因此浏览器/CDN 常把记录压到 ≈1×MTU（RFC 8449 的动机；Chrome 用过 1.2~1.4 KB 记录），用带宽换丢包恢复速度。

**QUIC 直接替换了记录层**（RFC 9001）：握手消息走 CRYPTO **帧**（流式、带 offset，重组由 QUIC 负责；rustls 的 QUIC 接口只有 `read_hs()/write_hs()`，进出都是裸握手字节）；应用数据用 QUIC 自己的 packet protection——密钥调度沿用 TLS 1.3，但加密单位是 QUIC packet，nonce = IV ⊕ packet_number（构造思想与 TLS 1.3 记录一致）。QUIC 关心的是 path MTU（初始包 UDP payload ≥ 1200、不超 PMTU 以避免 IP 分片），16384 在 QUIC 中没有地位。注意 QUIC 单密钥上限更紧：AES 每包密钥 2²³ 个包（RFC 9001 附录 B.1），比 TLS 的 2²⁴ 更小。

**DTLS（TLS-over-UDP）则必须迁就包大小**：记录 > PMTU 会触发 IP 分片（丢 1 片全丢、常被防火墙拦截），所以 DTLS 要做 PMTU 探测压记录大小；还要加 TCP 版不需要的机制——记录头加 epoch + 显式序列号（UDP 不保序、可重放），握手消息加显式 `fragment_offset/length`（TCP 流自带重组，UDP 没有）。

### 2.5 记录层有自己的 Nagle 吗？

**没有。** TLS 层不存在 Nagle 式算法（无定时器、不等 ACK、不攒批）。以 rustls 为证：`Stream::write` 在加密后**立即**调用 `write_tls` 把记录推向 socket，内部缓冲只在 socket 返回 `WouldBlock` 时暂存（背压 ≠ 攒批）。

但 Nagle 与 TLS 在 **TCP 层**相互作用：应用频繁写小记录时，socket 默认开启的 Nagle 等待 ACK + 对端延迟 ACK，会产生 ~40 ms 级停顿。行业惯例是对 TLS 连接设置 `TCP_NODELAY = on`（nginx 默认即 on）；TLS 库自身从不修改 socket 选项。TLS 侧最像「攒批」的机制是 `set_buffer_limit` + `flush`——但那是应用显式驱动的（类似 `TCP_CORK`），不是 Nagle 那种 ACK/时间驱动。

### 2.6 小写入的代价：写放大与合并规则（附实测）

**规则（源码级确定）**：

1. **每次 `write()` 调用至少独立成一条记录**——TLS 库不做跨调用的明文合并。即使 socket 暂时 `WouldBlock`，明文也已加密定型，之后只是把**已生成**的记录发出去。
2. **单次调用内的数据尽量合并**：一次 `write(100B)` 是一条记录；一次 `write_vectored()` 传 100 个 1 字节切片，也是一条记录（rustls 会把多个 iovec 拼成一个载荷再分片）。
3. 合并是**应用的责任**，不是 TLS 的——TLS 无法猜到你的消息边界，`write` 的语义就是「现在发这些」。

**实测**（`cargo run -p lesson05 --example one_byte_writes`，TLS 1.3，AES-GCM）：

| 实验 | 记录数 | 线上字节 | 放大倍数 |
|------|--------|---------|---------|
| 100 次 `write(1B)` | **100** | 2300 | **23.0×** |
| 1 次 `write(100B)` | 1 | 122 | 1.2× |
| 1 次 `write_vectored(100×1B)` | 1 | 122 | 1.2× |

每条 1 字节记录 = 5 B 头 + 1 B 数据 + 1 B 内部类型 + 16 B 标签 = 23 B，其中 22 B 是纯开销。代价不只是带宽：每条记录一次 AEAD 运算、一次 `write()` 系统调用、消耗一个序列号（向 §5.2 的 AES-GCM 2²⁴ 上限推进），接收方也要逐条验 tag。

**注意**：100 条小记录 ≠ 100 个网络包——TCP 会把它们合并进少量段（对 TCP 只是流字节）。真正的浪费发生在 TLS 层（上面的 22×）与系统调用层；若各次写入在时间上分散（如逐按键交互），还会撞上 §2.5 的 Nagle/延迟 ACK 停顿。

**正确做法**：应用层攒批后再一次 `write`；或用 `write_vectored`；或外面包 `std::io::BufWriter`（到容量/flush 才透传给 TLS）。

## 3. 保护记录 I：TLS 1.2 的三种形态

同一套记录头，载荷结构按密码套件分三种。

### 3.1 MAC 的精确定义（RFC 5246 §6.2.3.1）

TLS 1.2 的 MAC 覆盖的是「**记录头 + 内容**」而不仅是内容：

```
MAC = HMAC( MAC_write_key,
            seq_num(8B) || type(1B) || version(2B) || length(2B) || fragment )
```

注意 `seq_num`（序列号，§5）**不在线上传输**——发送方和接收方各自维护计数器，MAC 把它绑进来以防「记录被重放/重排/删除」。

常见 MAC 长度：HMAC-SHA1=20B、HMAC-SHA256=32B、HMAC-SHA384=48B。

### 3.2 CBC 套件：MAC-then-Encrypt 的完整流程

以 100 字节明文、AES-128-CBC + HMAC-SHA256 为例，一步步算：

```
① MAC:   输入 = seq(8) + 0x17 + 0x0303 + 0x0064 + 100B 内容 = 113 字节
          输出 = 32 字节 MAC
② 拼接:  100B 内容 + 32B MAC = 132 字节
③ 填充:  132 不是 16 的倍数 → 补到 144
          需追加 12 字节 = 11 个填充字节 + 1 个 padding_length 字节
          全部填 padding_length 的值：12 个 0x0B
④ 显式 IV: TLS 1.1+ 每条记录随机/递增 IV 16 字节，明文放在载荷最前面
⑤ 加密:  144 字节按 CBC 加密
⑥ 线上:  头 5B (length=16+144=160, 0x00A0) + IV 16B + 密文 144B = 165 字节
```

**为什么要 padding_length 字节还要全填同一个值？** 为了让接收方能校验填充合法性（读到最后一字节 n，检查前 n 个字节是否都等于 n）。而这个「可校验性」恰恰成了攻击面：

**Padding Oracle 攻击（原理）**：MAC-then-Encrypt 顺序意味着接收方**先解密、再验填充、最后才验 MAC**。如果「填充非法」和「MAC 错误」产生**可区分的响应**（不同的 alert、不同的处理时间），攻击者就得到一个「填充合法性预言机」：逐字节篡改密文末尾，观察哪种篡改通过了填充检查，即可不碰密钥恢复整段明文。Vaudenay 2002 年提出，TLS CBC 上的实践即 Lucky 13。缓解：常数时间处理、错误统一为 `bad_record_mac`；根治：弃用 CBC。

### 3.3 GCM 套件（TLS 1.2 已有 AEAD）

RFC 5288 定义，载荷结构简化为：

```
线上载荷 = explicit_nonce(8B) || 密文(=明文长度) || tag(16B)
```

- **nonce (12B)** = 4 B salt（从流量密钥派生，不传输）‖ 8 B 显式部分（线上传输，通常取序列号）
- **AAD (13B)** = `seq(8) || type(1) || version(2) || length(2)`——把 §3.1 的 MAC 头直接变成被认证的关联数据
- 没有 MAC 字段、没有填充；完整性与机密性由 GCM 的 tag 一次提供

## 4. 保护记录 II：TLS 1.3 的 AEAD（每个字节都对齐过源码）

### 4.1 与 1.2 的结构差异总览

| | TLS 1.2 GCM | TLS 1.3 |
|---|---|---|
| 真实内容类型 | 记录头里明文可见 | **加密在内部明文里**（线上恒为 0x17） |
| 填充 | 无 | 内部明文可选 padding（流量分析对抗） |
| nonce | 4B salt + 8B 显式 nonce（线上传 8B） | **静态 IV ‖ 异或序列号**（什么都不传） |
| AAD | 13B（含 seq） | 5B（= 记录头，seq 已隐含在 nonce 里） |
| 标签 | 16B | 16B |

### 4.2 内部明文：类型藏在密文里

```
内部明文 TLSInnerPlaintext = content(≤2¹⁴) || 真实类型(1B) || padding(≥0, 全 0)
```

- 解密后**从末尾向前**找第一个非零字节即真实类型，其后全零为 padding（全零/找不到类型 → 非法）
- 加密前总长上限 2¹⁴+1（内容 2¹⁴ + 类型 1B），解密去填充后内容 ≤ 2¹⁴
- 密文长度 = 内部明文 + 16B 标签，线上 length 字段因此 ≤ 2¹⁴+256

### 4.3 nonce 构造（worked example）

```
静态 IV（握手时从流量密钥派生，双方一致，不再变化）:
  4f 2a 91 c3  77 00 1b 8e  d2 5c aa f0        (12 B)

序列号 seq = 5 → 大端 64 位，左补零到 12 B 后与 IV 异或:
  IV :  4f 2a 91 c3 77 00 1b 8e d2 5c aa f0
  seq:  00 00 00 00 00 00 00 00 00 00 00 05
  XOR──────────────────────────────────────
  nonce:4f 2a 91 c3 77 00 1b 8e d2 5c aa f5   ← 只有末字节变了
```

序列号不占带宽（接收方按到达顺序自己计数），又天然保证「同密钥下 nonce 不重复」——这是把 §5 的换钥问题和 nonce 安全直接挂钩的设计。

### 4.4 AAD：就是那条 5 字节记录头

```
AAD = 0x17 || 0x03 0x03 || length_hi || length_lo
      （length = 密文长度，含 16B 标签）
```

防的是**记录头篡改**：改长度字段（截断/拼接攻击）、把记录移植到别的连接/方向，都会导致 tag 验证失败。

### 4.5 纠正一个常见错误说法

TLS 1.3 **不是** "Encrypt-and-MAC"，也不是 "MAC-then-Encrypt"，而是 **AEAD 单一原语**：加密与认证在一个经过证明安全性的结构里完成，tag 先验证、明文才可用。旧的「组合式」方案（MAC-then-Encrypt 产生 padding oracle、Encrypt-and-MAC 泄露 MAC 等泛构造缺陷）正是被它取代的原因。

## 5. 序列号与密钥生命周期

### 5.1 序列号

- 每个**方向、每套流量密钥**独立一个 64 位计数器，从 0 开始，每发/收一条记录 +1
- **从不上线传输**，但参与一切认证：1.2 的 MAC/AAD、1.2 GCM 的显式 nonce、1.3 的 nonce（异或进 IV）
- 作用：防重放、防重排、防删除——任何这类篡改都会让 MAC/tag 对不上

### 5.2 一把密钥能加密多少条记录？

nonce 是 96 位的，其中 64 位被序列号占据——但**远在序列号耗尽之前**，机密性就先退化（区分攻击的优势随加密量增长，CFRG AEAD Limits 分析给出安全上限）：

| 算法 | 单密钥安全上限 | rustls 行为（到限自动触发） |
|------|---------------|---------------------------|
| AES-128/256-GCM | 2²⁴ 条记录 | TLS 1.3：自动发 Key Update 换钥后继续；TLS 1.2：只能关连接 |
| ChaCha20-Poly1305 | 无实际限制（2⁶⁴） | 不需要中途换钥 |

这就是 TLS 1.3 **Key Update** 消息存在的主要理由之一：长连接（数据库连接池、gRPC 长流）跑到 2²⁴ 条记录时无感换钥，应用毫无感知。换钥后序列号**归零重数**，nonce 空间焕新。

## 6. 中间盒兼容与连接关闭

### 6.1 伪装的 ChangeCipherSpec

TLS 1.3 握手中，客户端（服务器也可能）在发完第一批握手消息后插入一条**毫无协议意义**的 CCS 记录：`14 03 03 00 01 01`（载荷恰好 1 字节 0x01）。唯一作用是让中间盒以为「马上要进入加密模式了」，别把后续 0x0304 的流量当异常掐断。接收方要求其载荷必须恰为 `[0x01]`，其余情况按非法处理。

### 6.2 close_notify 与截断攻击

TLS 的干净关闭 = 发一条加密的 Alert 记录（close_notify）。如果只关 TCP 不发 close_notify，接收方无法区分「对端正常发完了」和「攻击者剪断了连接」（截断攻击：砍掉响应尾部，让客户端以为转账页面只有半截）。**应用必须把「TCP EOF 但没有 close_notify」当错误处理**（rustls 返回 `ErrorKind::UnexpectedEof`），并由上层协议自带完整性边界（如 Content-Length）兜底。

## 7. 安全属性与常见误区速查

| 说法 | 真相 |
|------|------|
| 「TLS 1.3 是 Encrypt-and-MAC」 | ❌ 是 AEAD 单一原语，不属于任何旧组合 |
| 「TLS 1.2 都有填充」 | ❌ 只有 CBC 套件填充；GCM 无填充 |
| 「记录边界就是消息边界」 | ❌ 分片/合并使边界不可靠，上层要有自己的框架 |
| 「记录版本字段 = 协商版本」 | ❌ 兼容摆设，恒 0x0303；真协商在 supported_versions |
| 「TLS 1.3 记录头暴露内容类型」 | ❌ 加密记录线上恒 0x17，真类型在密文内 |
| 「记录长度是保密的」 | ❌ 长度字段明文，流量分析是记录层的固有泄露（可用 padding/缩小 fragment 缓解） |

## 10. 思考问题（附参考答案）

1. **为什么 TLS 记录有最大长度限制？**
   <details><summary>答案</summary>
   接收方在验证 tag 前必须按 length 缓冲整条记录，上限防内存 DoS；密码学需要
   有界单元做逐条认证；限制单条记录大小同时限制了解密延迟抖动和缓冲预算。
   （§2.1）
   </details>

2. **MAC 的作用是什么？和数字签名有什么区别？**
   <details><summary>答案</summary>
   MAC 是对称密钥的完整性+对端认证，快，但持有密钥的任何一方都能生成，无法向
   第三方证明来源（无不可抵赖性）；签名是非对称的，公钥可公开验证，慢，提供
   可第三方验证的真实性与不可抵赖。TLS 里记录用 MAC/AEAD（对端间足够），握手
   身份认证才用签名。（§3.1）
   </details>

3. **什么是 padding oracle 攻击？**
   <details><summary>答案</summary>
   MAC-then-Encrypt 下接收方先解密验填充、后验 MAC，若「填充错」与「MAC 错」
   响应可区分，攻击者逐字节篡改密文即可获得填充合法性反馈，不碰密钥恢复明文。
   缓解：常数时间+统一错误；根治：AEAD/弃用 CBC。（§3.2）
   </details>

4. **AEAD 相比传统 MAC+加密有什么优势？**
   <details><summary>答案</summary>
   单原语同时绑定机密性、完整性与关联数据，结构经证明安全，避开组合误用
   （padding oracle、MAC 信息泄露），一次遍历更快，API 更难用错。（§4.5）
   </details>
